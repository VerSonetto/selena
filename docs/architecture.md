# Selena Architecture

## Product shape

Selena has one Rust core and three surfaces:

- `selena` — ratatui terminal control room, which owns or attaches to the local service.
- `selena web` — axum server plus the shared React console.
- `selena desktop` — Tauri v2 shell with a custom title bar, loading the same local web console.

Web and desktop use the same `web/dist` build. The desktop WebView loads the loopback HTTP server so SSE, cookies, and API behavior are identical to the browser.

## Protocol matrix

Selena does **not** have a fixed Chat Completions egress. Every provider declares a protocol, and every public endpoint is an ingress protocol:

| ingress \ provider | Chat Completions | Responses | Messages |
|---|---|---|---|
| Chat Completions | passthrough | convert | convert |
| Responses | convert | passthrough | convert |
| Messages | convert | convert | passthrough |

- **Diagonal**: the request is forwarded in its original protocol. Only model routing/auth is applied; SSE bytes are relayed. Native-only features such as Responses state/hosted tools or Anthropic thinking/server tools remain intact.
- **Off-diagonal**: request decodes to a canonical IR, the target encoder emits the provider body, and the upstream response is decoded and encoded back to the ingress protocol.
- **Fail-fast**: native-only capability that cannot be represented in the target protocol returns `unsupported_feature`. Active hosted/server tool definitions, Responses state, and audio are never simulated.
- **Opaque history**: Anthropic thinking blocks, signatures, and server-tool result blocks cannot cross protocols by design. They are dropped with a conversion warning rather than rejected, so clients that replay full history (including Claude Code) can still use non-Anthropic providers. Selena never fabricates or replays a signature.

## Crate layout

```
crates/
  selena-protocol/  pure protocol IR, 3 codecs, SSE parser, conversion tests
  selena-core/      config, SQLite, providers, key pool, routing, secrets
  selena-server/    axum gateway, admin API, SSE bridge, embedded SPA
  selena-cli/       `selena` binary, command dispatch, TUI
  selena-desktop/   Tauri v2 shell
web/                React 19 + Vite + TypeScript console
```

Dependency direction: `selena-protocol ← selena-core ← selena-server ← selena-cli / selena-desktop`.

## Runtime lifecycle

- Data home: `~/.selena` (`SELENA_HOME` override).
- Default listener: `127.0.0.1:13697` (`SELENA_HOST`, `SELENA_PORT`). A custom port can be passed with `--port` or persisted in Settings → 服务与路由; a configured port change takes effect on the next service start.
- `runtime.json` contains PID, actual port, and one-time admin token.
- `selena` TUI starts the service if no healthy instance exists; `selena web` reuses a healthy instance and opens a tokenized admin URL.
- `selena desktop` spawns `selena-desktop(.exe)`, which starts or reuses the local service and loads the console.
- Same-protocol SSE is forwarded with backpressure; cross-protocol SSE uses `SseParser → StreamDecoder → CanonicalStreamEvent → StreamEncoder → SSE`.
- Model discovery: each provider's `GET {base_url}/models` is called with its auth headers, parsed tolerantly, grouped per provider, and cached for 120 seconds. The model pool page aggregates duplicate model IDs across providers; a failed provider is reported independently.
- Provider failures retry across keys only before downstream bytes are emitted. Once a stream starts, failures produce a protocol-native error/terminal event.

## Storage

SQLite WAL (`selena.db`) stores providers, provider keys, routes, client keys, request metadata, and settings. Provider secrets are encrypted with XChaCha20-Poly1305 using a local master key (or `SELENA_MASTER_KEY`). Request/response bodies are not stored by default.

## Security boundaries

- Admin API uses the runtime token; the console stores it only in localStorage for the current browser.
- Provider API keys never leave the server in plaintext after creation.
- Client API keys are hashed; only creation returns the secret once.
- The gateway accepts `Authorization: Bearer` and `x-api-key`. If no client keys exist, loopback requests are allowed for first-run convenience; adding a key closes that path.
- Non-loopback binds require deliberate configuration and should be placed behind TLS and an authenticated reverse proxy.

## Design

The shared console uses the **Ivory Studio** visual system with a Dusk companion. Theme mode supports `system`, `ivory`, and `dusk`; `system` follows `prefers-color-scheme` live. See `docs/design-system.md`.

## Windows-first release

The Windows bundle is generated by Tauri NSIS. The desktop executable is `selena-desktop.exe`; the console CLI is staged as a resource and copied beside it by an NSIS hook, then the install directory is appended to the user PATH. This makes `selena`, `selena web`, and `selena desktop` available in a new terminal.
